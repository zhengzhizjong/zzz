## 一、架构设计原则

| 原则 | 描述 |
|------|------|
| **DDD领域驱动** | 按业务领域划分微服务边界，充血模型，事件驱动 |
| **SaaS多租户优先** | 所有服务内置tenant_id隔离，数据行级共享库 |
| **CQRS读写分离** | 写强一致（MySQL主库），读高并发（ES/ClickHouse） |
| **AI First** | AI能力全链路嵌入，LLM统一网关调度所有AI能力 |
| **零信任安全** | 默认不信任，持续验证，最小权限 |
| **高可用可扩展** | 万店级水平扩展，99.99%可用性保障 |

### 5.2 CQRS适用场景矩阵

| 场景 | 写通道 | 读通道 | 一致性 | 响应要求 |
|------|--------|--------|--------|----------|
| 预约创建 | MySQL主库 | Redis缓存 | 强一致 | <100ms |
| 订单查询 | MySQL主库 | ES | 最终一致 | <500ms |
| 店长日报 | MySQL主库 | ClickHouse | 最终一致 | <2s |
| 客户搜索 | MySQL主库 | ES | 最终一致 | <300ms |
| 会员积分变更 | MySQL+EventStore | Redis | 强一致 | <50ms |
| AI问诊记录 | MySQL主库 | ES+ClickHouse | 最终一致 | <1s |
| 时段可用性查询 | - | Redis缓存 | 最终一致 | <50ms |
| 推广数据统计 | MySQL持久化 | Redis实时计数 | 最终一致 | <100ms |

## 六、预约锁档机制【V3.4新增】

### 6.1 机制概述

预约时段的并发安全是交易域的核心挑战。在高并发场景下（如热门技师、高峰时段），多个用户可能同时选择同一时段，需通过分布式锁+乐观锁双重保障确保时段不被重复预约。

### 6.2 架构设计

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      预约锁档机制架构                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  用户选时段                                                               │
│      │                                                                   │
│      ▼                                                                   │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │  第1层：Redis分布式锁（时段锁定）                                    │  │
│  │                                                                    │  │
│  │  锁Key: lock:{tenant_id}:appointment:{store_id}:{technician_id}   │  │
│  │         :{date}:{time_slot}                                        │  │
│  │                                                                    │  │
│  │  锁定时长: 5分钟（用户选时段后锁定，超时自动释放）                      │  │
│  │  锁Value: {user_id, lock_time, expire_time, request_id}           │  │
│  │  加锁方式: SETNX + EXPIRE（原子操作）                               │  │
│  │  释放条件: 用户确认预约 / 用户主动取消 / 超时自动释放                  │  │
│  └──────────────────────────────────────────────────────────────────┘  │
│      │ 加锁成功                                                          │
│      ▼                                                                   │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │  第2层：防重复校验（业务规则）                                       │  │
│  │                                                                    │  │
│  │  规则: 同一客户 + 同一门店 + 同一天 → 最多3个有效预约                 │  │
│  │  校验: SELECT COUNT(*) FROM appointment                            │  │
│  │        WHERE tenant_id=? AND store_id=? AND member_id=?            │  │
│  │        AND date=? AND status IN ('待确认','已确认','服务中')         │  │
│  │  Redis辅助:                                                        │  │
│  │    appt:count:{tenant_id}:{store_id}:{member_id}:{date} → 计数器   │  │
│  │    预约创建时INCR，取消/完成时DECR                                   │  │
│  └──────────────────────────────────────────────────────────────────┘  │
│      │ 校验通过                                                          │
│      ▼                                                                   │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │  第3层：MySQL写入 + 乐观锁（防并发冲突）                              │  │
│  │                                                                    │  │
│  │  Appointment表增加 version 字段:                                    │  │
│  │    UPDATE appointment                                              │  │
│  │    SET status=?, version=version+1, updated_at=NOW()               │  │
│  │    WHERE id=? AND version=?                                        │  │
│  │                                                                    │  │
│  │  冲突处理:                                                          │  │
│  │    version不匹配 → 抛出OptimisticLockException                     │  │
│  │    → 前端提示"数据已变更，请刷新重试"                                │  │
│  └──────────────────────────────────────────────────────────────────┘  │
│      │ 写入成功                                                          │
│      ▼                                                                   │
│  释放Redis锁（确认预约后主动释放，而非等超时）                             │
│  发布事件: AppointmentCreated → 更新时段缓存 → 通知技师                   │
│                                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 6.3 锁Key设计规范

| 维度 | 字段 | 说明 | 示例 |
|------|------|------|------|
| 租户 | tenant_id | SaaS多租户隔离 | 1001 |
| 门店 | store_id | 门店级隔离 | 2001 |
| 技师 | technician_id | 技师维度锁定，0表示不指定 | 3001 |
| 日期 | date | 预约日期 | 20260615 |
| 时段 | time_slot | 时段标识（HH:mm-HH:mm） | 14:00-14:30 |

**完整Key示例：** `lock:1001:appointment:2001:3001:20260615:14:00-14:30`

### 6.4 异常场景处理

| 场景 | 处理策略 |
|------|----------|
| 用户选时段后未操作（5分钟超时） | Redis Key自动过期释放，时段恢复可预约 |
| 用户选时段后主动取消 | 主动删除Redis Key，立即释放时段 |
| 分布式锁获取失败 | 返回"时段已被占用，请选择其他时段" |
| 乐观锁冲突（version不匹配） | 返回"数据已变更，请刷新重试" |
| Redis宕机 | 降级为MySQL行锁（SELECT FOR UPDATE），性能下降但保证正确性 |
| 防重复超限（>3个有效预约） | 返回"同一天同一门店最多预约3次" |

### 7.2 预约创建流程（写通道）

```
用户确认预约
    │
    ▼
┌─────────────────┐
│ 1.获取分布式锁    │  Redis SETNX lock:{tenant_id}:appointment:...
│  (5分钟超时)      │  失败 → 返回"时段已被占用"
└────────┬────────┘
         │ 成功
         ▼
┌─────────────────┐
│ 2.防重复校验      │  同一客户+同一门店+同一天 ≤ 3个有效预约
│                  │  超限 → 返回"预约次数超限"
└────────┬────────┘
         │ 通过
         ▼
┌─────────────────┐
│ 3.MySQL写入      │  INSERT appointment (强一致)
│  (主库事务)       │  含 version=1 (乐观锁初始值)
└────────┬────────┘
         │ 成功
         ▼
┌─────────────────┐
│ 4.释放分布式锁    │  主动DELETE锁Key（不等超时）
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 5.更新时段缓存    │  Redis: slot:{...}:{time_slot} → BOOKED
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 6.发布领域事件    │  AppointmentCreated → RocketMQ
│                  │  → 通知技师(企微消息)
│                  │  → 更新预约计数器
│                  │  → 同步至CQRS读模型
└─────────────────┘
```

### 7.3 预约修改/取消流程（事件驱动）

```
用户发起修改/取消
    │
    ▼
┌─────────────────┐
│ 1.乐观锁校验     │  UPDATE ... WHERE id=? AND version=?
│                  │  冲突 → 返回"数据已变更，请刷新重试"
└────────┬────────┘
         │ 成功
         ▼
┌─────────────────┐
│ 2.MySQL更新      │  UPDATE appointment SET status=?, version=version+1
│  (主库事务)       │
└────────┬────────┘
         │ 成功
         ▼
┌─────────────────┐
│ 3.发布领域事件    │  AppointmentCancelled / AppointmentModified → RocketMQ
└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────────────────────────────────┐
│ 事件消费（异步处理）                                               │
│                                                                   │
│ Consumer-1: 释放时段缓存                                          │
│   → Redis: slot:{...}:{time_slot} → AVAILABLE                    │

│                                                                   │
│ Consumer-2: 通知技师                                              │
│   → 企微消息: "您有一个预约已取消/变更"                              │

```

### 7.4 时段查询缓存策略

| 缓存维度 | Redis Key | 数据结构 | 过期策略 | 更新时机 |
|----------|-----------|----------|----------|----------|
| 门店+技师+日期 | `slot:{tenant_id}:{store_id}:{technician_id}:{date}` | Hash (time_slot → status) | 当日有效，次日自动过期 | 预约创建/取消/修改时实时更新 |
| 门店+日期(不指定技师) | `slot:{tenant_id}:{store_id}:0:{date}` | Hash (time_slot → 可用技师数) | 当日有效 | 预约创建/取消时实时更新 |
| 技师排班 | `schedule:{tenant_id}:{technician_id}:{month}` | Hash (date → work_shift) | 月末过期 | 排班变更时更新 |
| 预约计数 | `appt:count:{tenant_id}:{store_id}:{member_id}:{date}` | String (计数器) | 当日有效 | 预约创建INCR/取消DECR |

## 十七、关键设计决策

| 决策ID | 问题 | 决策 | 权衡 |
|--------|------|------|------|
| AD-001 | 多租户隔离级别 | 共享库+行级隔离(tenant_id) | 成本低vs租户故障隔离弱，初期合理 |
| AD-002 | 数据库分片键 | tenant_id + store_id 复合键 | 支持按租户和按门店的查询 |
| AD-003 | 消息队列选型 | RocketMQ 5.x | 事务消息+延迟消息+高吞吐 |
| AD-004 | OLAP选型 | ClickHouse | 列式存储+向量化执行+实时性好 |
| AD-005 | 缓存策略 | Redis集群+哨兵 | 高可用+性能平衡 |
| AD-006 | AI网关方案 | 自研Gateway+多模型路由 | 自主可控+按场景最优模型 |
| AD-007 | 服务网格 | Istio | mTLS+流量管理+可观测性 |
| AD-008 | 预约并发控制 | Redis分布式锁+MySQL乐观锁 | 双重保障，Redis锁快速失败+乐观锁兜底 |
| AD-009 | 推广归因模型 | 末次点击归因(Last-Click) | 简单直观，多触点场景可升级为多触点归因 |
| AD-010 | 埋点统计架构 | Kafka→Flink→ClickHouse | 实时性好+可扩展，成本适中 |
